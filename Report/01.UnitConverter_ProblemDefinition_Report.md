## 1. 배경

UnitConverter_18은 `unit:value` 형식의 길이 입력을 meter·feet·yard 등으로 변환하는 Python CLI 프로그램이다.  
현재 `UnitConverter.py`는 단위별 분기와 하드코딩된 비율로 동작하며, README에는 OCP·SRP·입력 검증·설정 외부화·동적 단위 등록·출력 포맷 선택 등 확장 요구가 정의되어 있다.

본 보고서는 **“변환기가 없다”**는 표면 요구가 아니라, Mom Test에서 드러난 **교차 검증 비용**을 문제의 중심으로 고정한다.

## 2. Mom Test 결과

### 2.1 페르소나

IoT 센서 대시보드 사이드 프로젝트를 돌리는 **스타트업 1인 개발자**.  
펌웨어(mm), 슬랙 요약(feet), 투자자용 문서(meter/yard)에 **같은 거리 값**을 넣을 때마다 검색·엑셀로 출처와 자릿수를 교차 확인한다.

### 2.2 진짜 문제 (한 문장)

> **같은 값을 여러 맥락(펌웨어·슬랙·문서)에 쓸 때 숫자가 어긋날까 불안해, 매번 출처·자릿수를 교차 검증하는 데 7~8분씩 쓴다.**

### 2.3 Mom Test 증거 3줄

1. `1250 mm` → feet 변환에 구글 검색·복사로 **7~8분** 소모.
2. 결과가 **4.1016ft / 4.10ft / 4.1ft**로 달라 위키와 converter 사이트를 열어 **소수 셋째 자리**까지 맞춤.
3. 같은 날 yard·meter도 필요해 변환을 **3회 반복**하고, 엑셀 `=A1*0.00328084`로 **재확인** *(“converter 있으면…”은 생각만, 검색+엑셀로 우회)*.

### 2.4 표면 문제 vs 진짜 문제

| 구분 | 내용 |
|:---|:---|
| **표면 문제** | “mm/feet/yard/meter 변환기가 없다” |
| **진짜 문제** | **단일 기준값**을 빠르게 확정하지 못해, 출처마다 다른 숫자를 교차 검증하는 데 시간이 새는 것 |
| **핵심 불편** | 변환 자체보다 **신뢰할 수 있는 하나의 기준값**을 재현·공유하지 못하는 것 |

## 3. 문제 정의

### 3.1 주제 (솔루션 최소화)

> **한 입력값을 meter/feet/yard 등 여러 단위로 동시에 쓸 때, 출처마다 숫자가 달라 교차 검증에 7~8분이 새는데 — meter를 단일 기준으로 모든 등가값을 한 번에 재현·검증할 수 있는 규칙·명령·테스트 루프로 그 비용을 관찰 가능하게 줄인다.**

“웹 converter”, “IoT 대시보드”, “mm 지원”은 주제에 포함하지 않는다.  
다루는 것은 **기준값 확정 · 일관 출력 · 재현 가능 검증**뿐이다.

### 3.2 R-G-I-O

| | 내용 |
|:---|:---|
| **Role** | meter/feet/yard를 여러 맥락에 동시에 써야 하는 1인 개발자; 이번 단계에서는 변환 규칙·검증 절차·테스트 설계자 |
| **Goal** | `unit:value` 한 번 입력으로 **meter 기준 단일 앵커**를 확정하고, 등록된 모든 단위의 등가값을 **한 패스**로 내며, 비율·앵커 순서·반올림 규칙을 바꾸면 테스트가 깨지게 고정한다 |
| **Input** | `unit:value` 문자열 *(예: `meter:2.5`, `feet:8.2`)*; 등록 단위 `{meter, feet, yard}`; 비율 `1m=3.28084ft`, `1m=1.09361yd`; 반올림 R-06 *(소수 1자리)* |
| **Output** | Rule · Command · (Skill) · Test Loop 문서화 및 RED-1~3 테스트 *(SC-1←RED-1, SC-2←RED-2, SC-3←RED-3)*. *설정 외부화·동적 cubit·JSON/CSV·전체 OCP 리팩터는 이번 Output 아님* |

### 3.3 성공 기준

| # | 기준 | Mom Test 연결 |
|:---:|:---|:---|
| **SC-1** | 동일 입력에 **meter 앵커 1개**를 먼저 확정하고, feet·yard 등 모든 출력이 그 앵커에서만 파생된다 | ② 출처별 상이한 숫자 — **단일 계산 경로** |
| **SC-2** | `feet:8.2`와 `meter:2.5`처럼 다른 단위 입력도 앵커·교차 등가가 **모순 없이** 일치한다 | ③ 3회 반복 + 엑셀 재확인 — **교차 맥락 일치** |
| **SC-3** | SC-1·SC-2를 Test Loop로 고정했고, 비율·앵커 순서·반올림 규칙 변경 시 테스트가 **의도적으로** 깨진다 | ① 7~8분 교차 검증 — **회귀 테스트로 절차 고정** |

### 3.4 이번에 하지 않을 것 (표면 문제)

| 하지 않음 | 이유 |
|:---|:---|
| mm 포함 범용 converter / IoT 대시보드 | 솔루션 선행; Mom Test 고통과 분리 |
| 구글 검색·엑셀 대체 UI | 기능 제안; 현 단계는 규칙·테스트 |
| 설정 JSON / cubit 동적 등록 / JSON·CSV 출력 | README 추가 요구이나 **초기 세션 범위 밖** |
| OCP·SRP 전체 리팩터 + TC 전부 한 번에 | Rule·Command·Test Loop 우선 |
| 반올림 “대충 비슷하면 통과” | SC-3·회귀 보호 무력화 |
| “converter 만들면 매일 쓸 거야?” | Mom Test 금지 가설 |

## 4. 세션 3 산출 — 8계층 (Rule · Command · Skill · Test Loop)

### 4.1 Rule

| ID | 규칙 |
|:---|:---|
| **R-01** | 입력 형식은 `unit:value` |
| **R-02** | 등록 단위만 허용: `{meter, feet, yard}` |
| **R-03** | **meter = 앵커**; 모든 변환은 meter 경유 |
| **R-04** | `1 meter = 3.28084 feet`, `1 meter = 1.09361 yard` 고정 |
| **R-05** | 한 입력 → 등록 단위 **전부** 출력 *(누락 금지)* |
| **R-06** | 출력 반올림 규칙 고정 *(README 예시: 소수 1자리)* |

### 4.2 Command

| Command | 설명 |
|:---|:---|
| `PARSE_INPUT(s)` | `(unit, value)` 파싱 또는 형식 오류 |
| `TO_METER_ANCHOR(unit, value)` | meter 기준값 반환 |
| `EMIT_ALL_EQUIVALENTS(anchor_m)` | `{meter, feet, yard}` 일괄 출력 |
| `CROSS_CHECK(a, b)` | 서로 다른 입력 경로의 앵커·등가 일치 여부 |

### 4.3 (Skill) — 적용 순서

1. `PARSE_INPUT`
2. `TO_METER_ANCHOR`
3. `EMIT_ALL_EQUIVALENTS`
4. *(선택)* `CROSS_CHECK`로 두 입력 경로 대조
5. 전부 일치하면 종료 *(검색·엑셀 루프 없음)*

### 4.4 Test Loop (RED)

| ID | 시나리오 | 기대 |
|:---|:---|:---|
| **RED-1** | `meter:2.5` | feet·yard가 README 비율과 일치 *(예: 8.2ft, 2.7yd)* |
| **RED-2** | `feet:8.2` vs `meter:2.5` | 앵커·교차 등가 모순 없음 |
| **RED-3** | 비율·앵커 순서·반올림 규칙(R-06) 변경 | RED-1 **의도적 실패** *(회귀)* |

*(GREEN / REFACTOR는 후속 세션)*
